# maho X / Threads 10주 콘텐츠 계획

**작성일:** 2026-08-04  
**대상 채널:** X, Threads  
**목적:** 파워유저·개발자·브라우저 workflow에 불만이 있는 사용자를 중심으로 maho의 제품 관점과 초기 관심을 축적한다.

---

## 1. 전략 결론

maho의 X/Threads는 단순 바이럴 계정이나 브라우저 뉴스 큐레이션 계정으로 운영하지 않는다.

> 브라우저를 쓰며 겪는 맥락 혼란과 통제 상실을 이야기하고, maho의 ergonomic workflow를 실제 사용 장면으로 보여준다.

바이럴은 콘텐츠의 본체가 아니라 **유통 방식**이다.

- **제품 특성:** 콘텐츠의 본체
- **사용자 문제·관점:** 콘텐츠의 이야기
- **큐레이션:** 소재 공급과 유입
- **바이럴 포맷:** 확산 방식

### 권장 콘텐츠 비중

- **40~45%:** 제품 사용 장면
- **25~30%:** 브라우저 문제와 관점
- **15~20%:** 관련 주제 큐레이션
- **5~10%:** 순수 공감·바이럴

### 포지셔닝 규칙

- 리드: Ergonomics — Spaces, split view, command bar, keyboard-first workflow
- 강한 받침: Privacy — local, no telemetry 등 확인된 사실만 사용
- 보조: AI when asked — never forced, never mandatory
- SNS·마케팅 이미지에서는 경쟁사명을 직접 노출하지 않는다.
- `calm / calmer`, `AI-first`, `agent-native`, 오픈소스 주장, 미검증 수치·후기는 사용하지 않는다.
- Profile 격리는 정확히 표현한다: **Space에 Profile을 배정하면 쿠키·세션·로그인이 분리된다.** 기본적으로 모든 Space가 자동 격리되는 것은 아니다.

## 2. 채널 운영 방식

### X

짧고 선명한 문제 제기, 제품 GIF/영상, 개발 로그, 질문과 답글 중심으로 운영한다.

- 주 3회 메인 게시물
- 평일 15~30분 타깃 계정 답글 및 대화
- 이미지·GIF·짧은 화면 녹화 적극 활용
- 한 게시물에는 CTA 하나만 둔다.

### Threads

X의 문장을 그대로 복사하지 않고, 같은 주제를 조금 더 설명적으로 전개한다.

- 주 3회 메인 게시물
- 3~5개 포스트의 짧은 스레드형 설명 활용
- 제품 사용 장면에는 이미지·짧은 영상 첨부
- 질문형 마무리로 대화를 유도한다.

### 주간 리듬

- **월요일:** Problem / Point of View
- **수요일:** Product / Workflow
- **금요일:** Conversation / Curation

## 3. 게시물은 텍스트만 올리는가?

아니다. 텍스트만으로 시작할 수는 있지만, maho는 브라우저 UI와 workflow가 차별점이므로 **제품을 보여주는 시각 자산이 반드시 필요하다.**

### 게시물 형식 믹스

| 형식 | 권장 비중 | 주 사용처 | 역할 |
|---|---:|---|---|
| 짧은 텍스트 포스트 | 35~40% | X, Threads | 문제 제기·관점·질문 |
| 실제 UI 스크린샷 | 20~25% | X, Threads | 기능을 정지 화면으로 설명 |
| 짧은 화면 녹화/GIF | 25~30% | X 우선, Threads | Spaces·Split view·Command bar·Profiles 시연 |
| 개발 과정 이미지/짧은 영상 | 10% | X, Threads | 계속 shipping되는 제품과 maker accountability 전달 |
| 외부 링크 큐레이션 | 5~10% | X, Threads | 관련 주제 유입과 maho 관점 제시 |

비율은 초기 운영 가이드이며, 실제 반응에 따라 조정한다.

### 각 형식의 사용 기준

#### 1. 텍스트

사용자 문제, 관점, 질문에 적합하다.

예:

> Tab overload isn’t the real problem.  
> Context overload is.

텍스트만 올릴 때도 마지막에는 대화형 CTA를 붙인다.

> How many browser contexts do you switch between every day?

#### 2. UI 스크린샷

정지 상태에서 기능 구조가 바로 이해되는 경우에 사용한다.

예:

- Work / Personal / Project Space가 보이는 화면
- Split view 상태
- Command bar가 열린 상태
- Space에 Profile을 배정한 설정 화면

스크린샷은 실제 제품 화면을 사용한다. 기능이 아직 구현되지 않았다면 목업임을 명확히 표시하거나, 출시 제품처럼 게시하지 않는다.

#### 3. 화면 녹화 또는 GIF

maho의 핵심 형식이다. 기능 설명보다 조작 결과를 보여준다.

예:

- Space를 전환하는 5~10초 녹화
- 두 페이지를 Split view로 여는 5~10초 녹화
- Command bar에서 명령을 실행하는 5~10초 녹화
- Space별 Profile을 배정하고 로그인 세션이 달라지는 흐름

영상 첫 1초에 결과나 문제를 보여준다. 긴 소개 화면이나 로딩 화면은 넣지 않는다.

#### 4. 개발 과정

실제 구현·테스트·릴리스 준비 화면만 사용한다.

예:

- 기능 구현 전후
- 실제 테스트 장면
- UI 결정 과정
- 버그 수정 과정
- 릴리스 준비 과정

확인되지 않은 출시 일정, 속도, 사용자 수, 성능 수치는 쓰지 않는다.

#### 5. 큐레이션

외부 링크만 던지지 않는다.

구조:

1. 외부 주제 요약
2. 왜 중요한지
3. maho 관점
4. 사용자 workflow와 연결
5. 질문 또는 CTA

예:

> Browsers are moving toward doing more on your behalf.  
> That makes explicit controls more important, not less.  
> A browser should make it clear when it is acting — and when it is waiting for you.

## 4. 10주 계획

### 1주차 — maho가 왜 필요한가

**목표:** maho를 새 브라우저가 아니라, 좋아했던 브라우저 도구를 계속 쓰고 싶은 사람을 위한 제품으로 소개한다.

**월요일 — 텍스트**

> Most browsers treat tabs as the unit of work.  
> They usually aren’t.  
> The real unit of work is context.

CTA: `How many browser contexts do you switch between every day?`

**수요일 — 브랜드 문구 + UI 이미지 또는 짧은 제품 영상**

> Spaces, split view, command bar.  
> The browser tools you liked — still shipping, still yours.

CTA: `Follow the build.`

**금요일 — 창업자 관점 텍스트**

> We’re building a browser for people who took browsers seriously.  
> Not a browser that tries to do everything for you.  
> A browser that gets out of the way.

CTA: `What makes a browser worth keeping?`

**Threads 확장:** 브라우저가 탭은 관리하지만 맥락은 관리하지 않는다는 내용을 4~5개 포스트로 전개한다.

---

### 2주차 — 탭이 아니라 맥락

**목표:** 탭 과잉을 context overload 문제로 재정의한다.

**월요일 — 텍스트**

> 40 tabs isn’t always the problem.  
> The problem is not knowing which tabs belong together.

CTA: `Do you organize tabs by project, client, or chaos?`

**수요일 — 화면 녹화**

업무 Space → 개인 Space → 프로젝트 Space를 전환하는 장면을 보여준다.

카피:

> Different work doesn’t need different windows.  
> It needs different contexts.

CTA: `Which Space would you create first?`

**금요일 — 텍스트 또는 간단한 밈 이미지**

> “Just close your tabs” is not a workflow.  
> Sometimes those tabs are your working memory.

CTA: `Agree or disagree?`

---

### 3주차 — Spaces

**목표:** Spaces를 maho의 대표 기능으로 인식시킨다.

**월요일 — 텍스트**

> Your browser history remembers pages.  
> It doesn’t remember what you were doing.

**수요일 — 실제 UI 스크린샷 또는 GIF**

> A Space is more than a folder for tabs.  
> It’s a place for a context to stay together.

실제 기능 범위를 넘어 자동 기억·자동 분류를 암시하지 않는다.

**금요일 — 질문형 텍스트**

> If you had three browser Spaces, what would they be?

답글 선택지: `Work / Personal / Side project / Something else`

---

### 4주차 — Split view

**목표:** Split view를 비교·참조·작성 workflow로 보여준다.

**월요일 — 텍스트**

> Switching between two pages is often slower than reading them side by side.

**수요일 — 화면 녹화 또는 전후 이미지**

예시 workflow:

- 문서 + 참고자료
- 코드 + 문서
- 영상 + 메모
- 상품 비교

카피:

> Two pages.  
> One window.  
> Less back and forth.

CTA: `What do you usually keep side by side?`

**금요일 — 텍스트 + 관련 UI 이미지**

> A good browser UI should help you compare things without making you lose the thing you were looking at.

---

### 5주차 — Command bar와 키보드 우선 workflow

**목표:** maho를 빠른 조작 중심 브라우저로 인식시킨다.

**월요일 — 텍스트**

> If you already know what you want to do, a menu shouldn’t make you search for it.

**수요일 — 5~10초 화면 녹화**

Command bar 열기 → Space 이동 → 탭 검색 → 명령 실행을 보여준다.

카피:

> The command bar is for when you already know the command.

CTA: `What browser action should never require three clicks?`

**금요일 — 질문형 텍스트**

> Mouse-first or keyboard-first?  
> Or does it depend on the task?

---

### 6주차 — Space별 Profile과 로그인 분리

**목표:** Chromium 기반 Profiles를 maho의 가장 강한 차별점으로 소개한다.

**표현 규칙:**

- 정확: `Assign a Profile to a Space when you want its logins and sessions separated.`
- 금지: `Every Space is automatically isolated.`

**월요일 — 텍스트**

> One browser window.  
> Three accounts for the same service.  
> Why should that be complicated?

**수요일 — 실제 제품 화면 녹화**

1. Work Space에 Work Profile 배정
2. Personal Space에 Personal Profile 배정
3. 동일 서비스의 로그인 세션이 다르게 유지되는 장면

카피:

> Same window.  
> Different contexts.  
> Separate logins when you choose.

CTA: `Would you use separate browser identities in one window?`

**금요일 — 텍스트**

> Profiles shouldn’t add more windows to your life.  
> They should help one window handle more than one context.

보조 문구:

> Your sessions stay separated when you assign them that way. Simple, explicit, and opt-in.

---

### 7주차 — 계속 shipping되는 제품

**목표:** maho의 지속성, 직접 책임지는 maker 관점을 전달한다.

**월요일 — 텍스트**

> A browser feature is only useful if the product keeps supporting it.

**수요일 — 실제 개발 과정 이미지 또는 영상**

기능 구현·테스트·버그 수정·릴리스 준비 중 하나를 보여준다.

카피:

> No changelog theater.  
> Just the work required to keep the browser moving.

**금요일 — 창업자 메시지**

> maho is built with a simple responsibility:  
> keep the useful parts useful, and keep shipping.

실제 팀 구조나 개발자 수를 언급할 때는 현재 사실을 확인한다.

CTA: `What browser feature deserves better maintenance?`

---

### 8주차 — AI는 운전대가 아니다

**목표:** AI-first가 아닌 hand-on-wheel 원칙을 전달한다.

**월요일 — 텍스트**

> Not every browser task needs an agent.  
> Sometimes you just need a better command.

**수요일 — 제품 원칙 카드 또는 짧은 화면 영상**

> AI when you ask.  
> Never forced.  
> Never mandatory.

CTA: `What would you let a browser AI do — and what would you never delegate?`

**금요일 — 텍스트**

> A browser should not surprise you with actions you didn’t ask for.

---

### 9주차 — Privacy를 신뢰 받침으로 제시

**목표:** privacy를 리드 훅으로 세우지 않고, 신뢰 근거로 설명한다.

**월요일 — 텍스트**

> A browser is where your work, accounts, and habits meet.  
> Its defaults matter.

**수요일 — 사실 기반 제품 설명 카드 또는 UI 이미지**

> Local data.  
> No telemetry.  
> AI only when you want it.

현재 배포 상태·검증 범위가 확정되지 않은 문구는 `designed to` 등으로 조정한다.

**금요일 — 질문형 텍스트**

> What do you check before trusting a browser?

답글 선택지: `Data storage / Telemetry / Extensions / AI behavior / Company accountability`

---

### 10주차 — 정리와 초기 사용자 모집

**목표:** 9주간의 메시지를 하나의 제품 인식으로 묶고, 준비된 전환 경로로 연결한다.

**월요일 — 텍스트 + 기능 콜라주 또는 짧은 영상**

> The browser tools you liked:  
> Spaces.  
> Split view.  
> Command bar.  
> Still shipping. Still yours.

**수요일 — 핵심 workflow 화면 녹화**

Space 생성 → Space 전환 → Split view → Command bar → Space에 Profile 배정 흐름을 연결한다.

카피:

> One browser for the way your work actually changes throughout the day.

**금요일 — 초기 사용자 모집**

> We’re building maho for people who care about how a browser feels to use.  
> If Spaces, split view, command bars, and separate contexts matter to you, we’d like your feedback.

CTA는 실제 준비 상태에 따라 하나만 선택한다.

- Waitlist가 있으면: `Join the waitlist.`
- 테스트 빌드가 있으면: `Try the build.`
- Discord가 중심이면: `Join the Discord.`
- 공개 경로가 아직 없으면: `Follow the build.`

## 5. 게시물 제작 규칙

### 제품 게시물

기능 이름만 설명하지 말고 다음 순서로 구성한다.

1. 사용자의 상황
2. 불편한 지점
3. maho에서의 조작
4. 결과
5. CTA

예:

> Work, personal, and project tabs are easy to mix together.  
> Create a Space for each context.  
> Switch without opening another window.  
> Keep the current work together.  
> Which Space would you create first?

### 영상 규칙

- 첫 1초에 결과나 문제를 보여준다.
- 5~15초 길이를 우선한다.
- 실제 UI와 실제 조작을 사용한다.
- 로딩·빈 화면·불필요한 커서 이동을 제거한다.
- 자막 없이도 이해되도록 화면에 짧은 라벨을 둔다.
- 설명을 영상에 모두 넣지 말고 게시물 텍스트에서 보충한다.

### 이미지 규칙

- 제품 UI가 핵심이면 실제 스크린샷을 우선한다.
- 마케팅용 카드가 필요하면 한 장에 하나의 주장만 넣는다.
- 경쟁사 로고·이름을 넣지 않는다.
- 목업 UI를 실제 기능처럼 게시하지 않는다.
- “프라이버시 브라우저”만 크게 내세우지 않는다.

### 텍스트 규칙

- 첫 문장은 혼자 읽어도 이해되어야 한다.
- 한 게시물에는 한 가지 주장만 둔다.
- 과장된 수치·후기·출시일을 만들지 않는다.
- CTA는 하나만 둔다.

## 6. 측정 방법

매주 금요일 다음 항목만 기록한다.

1. 가장 많이 공유된 훅
2. 가장 많은 질문을 만든 기능
3. 조회수는 높지만 제품과 연결되지 않은 주제
4. 다음 주에 반복할 메시지
5. 버릴 메시지
6. 프로필 방문·팔로우·저장·공유·답글·링크 클릭
7. Spaces·Profiles·Split view에 대한 구체적 관심 표현

초기에는 좋아요보다 다음을 더 중요하게 본다.

- 저장·공유: 참고할 가치가 있었는가
- 답글: 실제 문제를 건드렸는가
- 프로필 방문: 제품 관심으로 이어졌는가
- 링크 클릭·Discord·waitlist: 전환 의도가 있는가
