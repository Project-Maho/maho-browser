## Summary

Adding a `maho-browser-mcp` crate with `rmcp = { features = ["server", "transport-io"] }` to the same Cargo workspace as `maho-agent` (which uses `rmcp = { features = ["client"] }`) is **safe**. Cargo unifies all features onto a single `rmcp v1.7.0` compilation unit, and both crates compile without error.

## Analysis

Cargo's feature unification merges all requested features for a given crate version into one compilation unit. For `rmcp v1.7.0`:

1. The `client` and `server` features are **additive and independent** — they gate separate type exports and impl blocks but do not conflict.
2. The `transport-io` feature adds stdio transport support, which pulls in `tokio` I/O traits. These are already transitively available via `maho-agent`'s tokio dependency.
3. The `default` feature (which includes `base64`, `macros`, `server`) was already being pulled in by one of maho-agent's transitive dependencies (likely via swiftide-agents -> rmcp default).

The rmcp crate was designed for exactly this pattern — a single process hosting both MCP client (connecting to external tools) and MCP server (exposing tools to external clients) simultaneously.

## Verdict

### `SAFE-TO-UNIFY`

No workspace split, no `[patch]` section, no feature isolation is needed. The `maho-browser-mcp` crate can safely declare `rmcp = { version = "1.7", features = ["server", "transport-io"] }` alongside `maho-agent`'s `rmcp = { features = ["client"] }`.

## Recommendation for Wave 2A

```toml
# maho/crates/maho-browser-mcp/Cargo.toml
[dependencies]
rmcp = { version = "1.7", features = ["server", "macros", "transport-io"] }
```

Consider also adding `"macros"` and `"schemars"` features (as mail does) for the `#[tool]` procedural macro and JSON Schema derivation — these are already unified into the workspace anyway via default features.
